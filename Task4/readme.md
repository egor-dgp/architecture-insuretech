### osago-aggregator: хранилище и API

#### Хранилище

Да, отдельное хранилище требуется:

- Сохранять заявки ОСАГО, их статус по каждой страховой компании и промежуточные ответы.
- Хранить correlation ID: `osagoRequestId`, `insurerRequestId`, статусы по каждой компании.
- Держать данные для повторного опроса `get-offer`, ретраев и технического логирования.

#### API для core-app

osago-aggregator — backend‑backend сервис, core-app общается с ним по REST/HTTP (внутренний API).

**Методы:**

- `POST /api/osago/quotes`  
  Вход: данные заявки (авто, водитель, регион и т.п.).  
  Выход: `osagoRequestId` и первые предложения, если они успели прийти.

- `GET /api/osago/quotes/{osagoRequestId}`  
  Возвращает список предложений по всем страховым, которые уже ответили, и статусы по остальным.

**Внутреннее поведение osago-aggregator:**

- При `POST`:
    - создаёт запись в своей БД;
    - синхронно вызывает `create-application` у страховых (по очереди или параллельно);
    - сохраняет `insurerRequestId` для каждой страховой;
    - запускает фоновые процессы для опроса `get-offer` до 60 секунд; фронт отображает все предложения, пришедшие за эти 60 секунд.

### Интеграция core-app ↔ osago-aggregator

#### Паттерны отказоустойчивости

- **Timeout**:
    - core-app не должен ждать osago-aggregator бесконечно;
    - таймаут на запрос `POST /api/osago/quotes` — 2–5 секунд.

- **Retry**:
    - 1–2 ретрая с экспоненциальной задержкой при сетевых ошибках, не при 4xx.

- **Circuit Breaker**:
    - между core-app и osago-aggregator;
    - защищает core-app от перегрузки, если osago-aggregator устойчиво падает или сильно тормозит.

- **Rate Limiting**:
    - на уровне Ingress или внутреннего API, чтобы ограничить количество запросов от core-app к osago-aggregator в пике.

### API для веб‑приложения (frontend) и интеграция с core-app

**REST‑API:**

- `POST /api/osago/quotes` — фронт отправляет заявку.
- `GET /api/osago/quotes/{id}` — фронт опрашивает прогресс и показывает новые предложения по мере появления.

**Таймбокс 60 секунд на стороне фронта:**

- фронт делает регулярный polling (например, каждые 2–3 секунды в течение минуты);
- каждый ответ `GET` возвращает актуальный список найденных предложений.

Интеграция: HTTPS REST через ALB/Ingress на core-app.

---

### Интеграция osago-aggregator ↔ страховые компании

Все страховые компании предоставляют 2 REST‑метода:

- `create-application`
- `get-offer`

Поведение osago-aggregator:

- При создании заявки:
    - отправляет `create-application` во все компании;
    - сохраняет их `applicationId`/`requestId`.
- Периодически опрашивает `get-offer` для каждой компании до 60 секунд (фронт ограничен 60 секундами ожидания).

#### Паттерны отказоустойчивости

- **Timeout**:
    - для каждого внешнего REST‑вызова, чтобы не блокироваться на одном коннекте дольше, чем заданный предел.

- **Retry**:
    - 1–3 ретрая с backoff для идемпотентных операций;
    - `get-offer` рассматривается как идемпотентный; `create-application` — с осторожностью.

- **Circuit Breaker**:
    - на каждом endpoint страховой;
    - при устойчивых ошибках или деградации конкретной страховой breaker отключает её, а osago-aggregator возвращает, что предложение от этой компании временно недоступно.

- **Rate Limiting**:
    - ограничение частоты запросов к каждой страховой, особенно по `get-offer`;
    - например, лимит запросов в секунду на компанию.

При 2,5k одновременных пользователей будет много параллельных запросов к страховым:

- osago-aggregator развёрнут в нескольких репликах;
- паттерны (Circuit Breaker, Rate Limiting) применяются:
    - либо в коде каждого экземпляра сервиса;
    - либо на уровне API‑gateway/sidecar (service mesh);

---

### Учёт множественных реплик сервисов

Паттерны (Rate Limiting, Circuit Breaker, Retry, Timeout):

- реализуются в клиентских библиотеках core-app и osago-aggregator (например, Resilience4j/Envoy);
- либо на уровне Ingress/Service Mesh.

Наличие нескольких реплик:

- не меняет необходимость применения паттернов;
- влияет на настройки:
    - Circuit Breaker обычно настраивается на инстанс клиента;
    - Rate Limiting может быть реализован на Ingress (общий лимит для всех реплик) или локально на Pod.
